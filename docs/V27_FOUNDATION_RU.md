# Linked by Light v27 — Foundation & Stability

**Статус:** кандидат в PR. Изменения находятся в `feat/v27-foundation-stability`, не объединены с `main` и не развёрнуты на Render. **Игровая версия остаётся 26.0.0, WebSocket-протокол 4, кампания 137 уровней (0–136)**. v27 — технический этап без изменения игрового контента.

## 1. Аудит исходной v26

- `server.js` до изменений: около 580 строк с обработчиками HTTP, WebSocket, сохранений, комнат и тиков.
- `cloud-store.js` сохранял полный зашифрованный снимок всех комнат в одну строку `linked_light_room_state` с ключом `server`. Состояние базы не проверялось после записи на уровне приложения.
- Локальный `linked-light-rooms-v11.json` писался атомарным переименованием, но при повреждении JSON отсутствовала резервная проверяемая копия.
- Идентификаторы действий хранились как временные Set без повторной выдачи ранее полученного результата и без постоянного хранения после рестарта.
- Компоненты истории v20/v21/v23 и базовая физика серверно-авторитетны. Переподключения, ограничения запросов, шифрование и CI уже существовали.
- `/health` сообщал только о работоспособности процесса, без состояния облачных сохранений. Это правильно для liveness, но недостаточно для диагностики готовности.

## 2. Data Integrity: v11 без потери обратной совместимости

Новый модуль `room-checkpoint.js` сохраняет **три файла** при заданном `SAVE_DIR`: исходный `linked-light-rooms-v11.json` без изменения структуры, журнал `.v27` с `schema:27`, SHA-256 и возрастающей ревизией, предыдущий `.v27.bak`. Используются временный файл, права `0600` и атомарное переименование. Запись любого нового файла не отменяет читаемость старого v26 формата.

При старте сервер проверяет структуру и контрольную сумму и выбирает подходящий источник. Если основной JSON или журнал повреждён, может использовать более старую проверенную резервную копию. Если после v27 был запущен v26 и он сделал более новый legacy checkpoint, v27 допускает восстановление этого состояния.

У облачных записей добавлено необязательное поле `savedAt`. Сервер не должен перезаписывать недавно восстановленные комнаты более старым облачным снимком. Рекорды и профили продолжают использовать прежний `version:11`.

**Важно:** локальная проверка SHA-256 выявляет случайную порчу, а не заменяет шифрование или аутентификацию. При аварийном выключении между периодическими сохранениями последние игровые действия всё равно могут быть потеряны; непрерывный журнал всех движений не ведётся.

## 3. Миграция Supabase и ротация ключей

Создана **аддитивная SQL-миграция** `database/migrations/20261116_v27_room_checkpoints.sql`. Она добавляет `linked_light_room_snapshots` — историю зашифрованных контрольных снимков с RLS, запретом публичного доступа, индексом по времени и удалением устаревших записей сверх последних 24. Таблицы v26 не удаляются.

Прежде чем включить архивирование:

1. Получить независимую резервную копию таблиц `linked_light_room_state` и `linked_light_cloud_saves` в своём проекте Supabase.
2. Выполнить SQL-миграцию на **отдельном staging Supabase**, проверить созданную таблицу, grants и RLS.
3. Повторить миграцию на production только после согласования выпуска.
4. После этого включить на сервере `LL_V27_ARCHIVE=1`, проверить запись в `linked_light_room_snapshots` и восстановление из неё.

При отсутствии `LL_V27_ARCHIVE=1` новая таблица **не требуется**, а запись идёт через существующий `linked_light_room_state`.

Для разделения ключа данных и ключа API можно задать `LL_ROOM_ENCRYPTION_KEY` как **64 шестнадцатеричных символа**. Сгенерировать значение локально:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Нельзя записывать значение в Git, URL, клиентский JS или логи. Новая версия при этом записывает **два слота**: `server` (зашифрован совместимым с v26 способом на основе текущего ключа Supabase) и `server-v27` (новым независимым ключом). Старый сервер v26 продолжит читать `server`. Если старый ключ Supabase уже ротирован, `LL_ROOM_LEGACY_SERVICE_KEY` временно разрешает v27 прочитать старый слот. **Не менять ключи и не удалять старый сервисный ключ до проверенного восстановления**.

Возможность чтения архива не заменяет off-site backup: при компрометации базы и серверного секрета история тоже может быть затронута.

## 4. Network Reliability

Новый `action-replay-cache.js` хранит по роли последние **128** подтверждений мутаций. Каждая операция с `actionId` привязывается к хешу полного набора её параметров. Повтор того же запроса возвращает **тот же результат** и `replayed:true` без повторного изменения игрового состояния. Повтор идентификатора с другим действием отклоняется. Кэш включён в серверные снимки комнаты, поэтому выдерживает переподключение и штатный рестарт.

Ранее обработанные ID за пределами окна 128 действий не гарантируют строго exactly-once при очень позднем повторе; для абсолютной гарантии понадобился бы постоянный журнал транзакций. Просмотр v25-реплеев является операцией чтения и может быть запрошен повторно.

Старая WebSocket-сессия после переноса роли на новый сокет больше не должна менять комнату. Парсер теперь отклоняет некорректный UTF-8 с кодом WebSocket 1007. Обработка текстовых фрагментов, ping/pong, масок и ограничений очереди вынесена в тестируемый модуль.

## 5. Modular Architecture и Security Hardening

- `websocket-transport.js`: RFC6455 кадры, фрагментация, маски, строгая UTF-8 декодировка и backpressure.
- `room-checkpoint.js`: формат, контрольная сумма и атомарный локальный журнал.
- `action-replay-cache.js`: ограниченная дедупликация и подтверждение сетевых команд.
- `runtime-monitor.js`: готовность, время успешной записи, ошибки и агрегированная диагностика.
- `cloud-store.js`: явное подтверждение upsert, двойное шифрованное сохранение и необязательный архив.

Проверки прав ролей, предельных размеров сообщений и ограничения частоты запросов сохраняются от v26. `LL_ROOM_ENCRYPTION_KEY` позволяет не использовать ключ API в качестве постоянного ключа данных. Администратор видит диагностические сведения только с корректным `LL_ADMIN_TOKEN`.

**Незавершённая архитектурная работа:** основной `server.js` всё ещё управляет логикой жизненного цикла комнаты и игровыми действиями; не стоит разбивать его на множество сервисов до дополнительных тестов наблюдаемого поведения.

## 6. Monitoring & Recovery

- `/health` остаётся **liveness** (`200`, `ok:true`), чтобы хостинг не перезапускал игру только из-за краткого сбоя Supabase.
- `/ready` — новая **readiness**-проверка: наличие требуемого хранилища, давность успешной записи, состояние первого запуска. Возвращает `503` при устаревших резервных копиях, если подключено облако; не возвращает личные данные игроков.
- `GET /api/admin/v22/overview` дополнен разделом `storage`: успехи и ошибки сохранений, время последней записи и восстановления, причины из фиксированного набора кодов (без сырых секретов).
- Периодичность резервных копий не меняется: локальный файл при `SAVE_DIR` — 12 сек., Supabase — 30 сек. Завершение процесса по SIGTERM инициирует финальный flush.

При `LL_REQUIRE_DURABLE_STORAGE=1` endpoint `/ready` не будет считать экземпляр готовым без сконфигурированного Supabase. **Не переключайте Render healthCheckPath на `/ready` без отдельного плана; текущий `/health` остаётся стабильным.**

## 7. E2E QA / тесты

```bash
npm test
node --check server.js
node --check websocket-transport.js
node --check action-replay-cache.js
node --check room-checkpoint.js
node --check runtime-monitor.js
```

Добавлены модульные проверки повреждённых JSON/хешей, несовместимых миграций, отката v26, ключей AES, хранения actionId, отклонения старых WebSocket-команд, строгого UTF-8 и деградации `/ready`. Добавлен реальный интеграционный тест двух WebSocket-игроков с восстановлением после рестарта и проверкой сохранённого `actionId`.

Отдельный CI workflow **v27 browser E2E (Chromium + WebKit)** запускает полноценные браузеры (настольное и мобильное окно), создаёт комнату v23, подключает второго пользователя, проверяет отображение совместной игры и переподключение после перезагрузки страницы. Это тест браузерных движков в CI, **не проверка физического iPhone**.

Оставшиеся обязательные ручные проверки: Windows Chrome и iPhone Safari в разных сетях; закрытие Safari и возврат; восстановление роли и уровня после перезапуска; реальная запись и чтение Supabase; откат сервера и проверка ключей; завершение всех 137 уровней или эквивалентный полный acceptance pass.

## 8. Release gate и безопасный откат

1. Все CI jobs, включая браузерный E2E и Render-Free-class simulation, должны завершиться успешно.
2. Применить миграцию и конфигурацию сначала в staging, не на production.
3. Проверить восстановление тестовых данных и smoke `version:26.0.0`, `protocol:4`, 137 уровней.
4. До production сохранить независимый экспорт базы и проверить возможность отката.
5. Только после ручной приёмки, отдельного разрешения на merge и соответствующего окна обслуживания объединять PR. После развёртывания Render отдельно проверить фактический SHA.

**В этом PR ни миграция в действующей Supabase, ни изменение секретов Render, ни объединение в `main` не выполняются.**
